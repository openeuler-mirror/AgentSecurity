# AgentMoss 脚本分析引擎（L1.2_L2.3 Script Engine）

> **覆盖层**：本引擎产出脚本内容后供 **L1.2（脚本内容 L1 扫描）** 与 **L2.3（脚本内容
> L2 扫描）** 两处消费（见 [DETECTION_PRIORITY.md](DETECTION_PRIORITY.md) §1 顺序表）。
> 文件名的 `L1.2_L2.3_` 前缀即指这两层——脚本内容分析本身是**跨层独立引擎**，不属于
> 某一个 L 小层。

> 这是脚本内容分析的**独立引擎**架构文档。操作流程（如何改规则、如何提交）见
> [MAINTENANCE_WORKFLOW.md](MAINTENANCE_WORKFLOW.md)。本文讲**引擎是什么、怎么工作、
> 能力边界、如何扩展**。

## 一、为什么要有独立引擎

脚本内容分析（用户执行 `bash deploy.sh` 时，分析器要读脚本内容、判断其是否危险）早期是
`script_content_analyzer.py` 一个 1000+ 行的单体：预处理、分支感知、递归追踪、关键词扫描
揉在一起。问题：

1. **控制流不分**：整段脚本全文扫描，`case $1 in clean) rm ~/.ssh/id_rsa` 里实际走
   `backup)` 分支也被误拦（`NEW-FP-O`）。
2. **深层链漏追踪**：固定 `max_depth=3`，第 4 层后的危险整层跳过（`NEW-FN-H`）。
3. **子脚本参数丢失**：`bash child.sh backup` 的 `backup` 不传给 child，child 分支感知
   用错参数（`NEW-FN-I`）。
4. **单语言**：只能内联提取 shell，Python/Node 子脚本无法追踪。
5. **双端漂移**：Python/TS 各写一份镜像，改一漏一。

引擎把它拆成三层，单一职责、双端镜像。

## 三、三层职责与数据流

### 1. LanguageBackend（解析 → IR）

把源脚本文本解析成**语言无关的中间表示**。加新语言 = 新出一个 Backend 产出同样的 IR，
Tracker/Scanner 不动。

```python
# base.py 抽象
class LanguageBackend(ABC):
    language: str
    def parse(self, content: str, entry_args: list[str] | None) -> ScriptIR: ...
```

**ShellBackend**（shell 解析）解析：

- **case**：`case $1 in ... esac` / `case ${1} in`，selector 可从入口参数绑定时选分支。
  - 支持多值 `clean|reset)`、兜底 `*)`、单行/多行分支体。
  - `case $MODE in`（命名变量）→ P1 不可绑定，升级 LiteSE P3 追踪 `MODE=clean` 后选择。
- **if**：`[ "$1" = "clean" ]` / `[ "$1" == clean ]` / `[[ "$1" = x ]]` 字符串相等条件。
  条件可静态求值则选分支；否则（`[ -f /x ]`、符号变量）→ 升级 LiteSE，仍不可确定才 fail-closed。
- **循环**（`while`/`for`/`until`）：**体全部保留**（保守——执行次数运行期未知，
  不可证明不可达，剔除会漏报）。
- **参数绑定**：`$1/$2/${1}/${1:-default}/$@/$*` 替换为入口参数值。
- **子脚本调用提取**：`bash child.sh backup` → `ScriptCall(path="child.sh", args=["backup"],
  interpreter="bash")`；解释器含 bash/sh/zsh + python/node/ruby/perl/php/lua。

**PythonBackend**（python 解析，stdlib `ast`）解析：

- **sys.argv 绑定**：`sys.argv[N]` 绑定入口参数（等价 shell 的 `$N`）；
  简单赋值追踪 `mode = sys.argv[1]`（含 `if len(sys.argv) > 1 else "default"` 三目形态）。
- **if/elif 链**：条件可静态求值（`==`/`!=`/`in` 字面量元组/`len(sys.argv) > 1`/
  `__name__ == "__main__"`/`and`/`or`/`not`）→ 选分支；不可求值 → 整链保留（fail-closed）。
- **循环/try/with/match**：体全部保留（保守），体内 if 仍按静态条件剪枝。
- **def/class**：整树保守保留（调用时环境未知，不可证明不可达），不做内部剪枝。
- **子脚本调用提取**：`subprocess.run(["bash","x.sh",arg])` 列表形式 +
  `os.system("bash x.sh arg")` 字符串形式（复用 shell 正则）+ `from . import x` 相对导入。
- **预算**：超 `MAX_LINES=500` 行 → fail-closed 全文本（与 symbolic 红线一致）。

**后端分发**：`tracker.py::_pick_backend` / `tracker.ts::pickBackend` 按脚本文件扩展名
选择 backend（`.py` → PythonBackend，其余 → ShellBackend），支持跨语言调用链
（shell 调 python、python 调 shell 均可递归追踪）。

### 2. RecursiveTracker（跨脚本递归）

消费 IR.calls，驱动调用链递归。独立于语言。

预算模型（改这些值要双端同步）：

| 参数 | 默认 | 防什么 |
|---|---|---|
| `max_depth` | 14 | 超深链（旧版是 3，导致深层漏追踪 NEW-FN-H） |
| `max_nodes` | 64 | 花式链巨大化撑爆内存 |
| `max_file_size` | 2MB / 脚本 | 单文件超限 |
| `max_total_size` | 8MB | 全链累计大小 |

**循环检测**：DFS 的 `visiting` 集合，A→B→A 直接跳过，不无限递归。

**跨脚本参数**：每个子节点用**它自己的 `ScriptCall.args`** 做分支感知，不是入口参数——
这就是修复 NEW-FN-I 的关键。

### 3. 扫描层（只消费 IR）

`scan_script_chain_with_l1` / `scan_script_chain_with_l2`（facade 内）对每个节点的
`IR.reachable_content`（可达内容）跑 L1/L2。L3 的 prompt 也基于可达内容。
**Scanner 不知道脚本长什么样，只认 IR。**

### 4. LiteSE 符号环境执行器（ShellBackend 内置，升级路径）

`backends/symbolic.py`（Python）/ `script-engine/symbolic.ts`（TS）——在 P1
（字面量 case/if）处理不了时**升级接管**，解决四类真实场景：

| 层 | 场景 | 示例 | 方法 | 复杂度 |
|---|---|---|---|---|
| P1 | 字面量匹配 | `case $1 in clean)` | 参数替换+字符串相等 | O(N) |
| P2 | 变量拼接 | `case "prefix${1}suffix"` / `${1}${2}` | 表达式求值（SVal fold） | O(表达式) |
| P3 | 内部命名变量 | `MODE=clean; case $MODE` | 顺序执行 + 符号环境 env | O(行) |
| P4 | glob / 数值分支 | `case $1 in bak*)` / `[ "$1" -gt 5 ]` | glob→正则 / 整数比较 | O(模式) |
| P5 | 熔断降级 | 超预算/不可建模 | 回退全文本 | O(1) |

**SVal 统一符号值**：`concrete`（已确定）/ `symbol`（未解析）/ `expr`（表达式，可折叠）。
所有变量、表达式求值结果统一 SVal 表示；expr 的全 concrete 子节点自动合并为 concrete。

**性能红线（硬约束，全程不突破）**：
- 复杂度：全链路线性，无回溯、无路径枚举、无状态空间爆炸
- 预算：行数 500 / 分支 50 / 变量 200，任一超限立即回退全文本
- 实测：单脚本 4~8ms（P4 glob 场景最高），峰值 RSS 23.7MB 与旧版持平

## 四、fail-closed 设计（安全底线）

引擎是"能静态证明的精确切片"，不是"穷举"。以下情况**强制回退全文本扫描**（保守拦截，
不引入漏报）：

- 入口无参数 / 参数与任何 case 分支都不匹配（也无 `*）`
- `case $MODE` / `$VAR` 命名 selector（无环境变量上下文）
- if 条件不可静态求值（文件存在性、命令返回值）
- 参数值本身含 `$(...)` 命令替换 / 环境变量（绑定不了，保持原文）
- **嵌套 case（case-in-case）内层无法安全判定**：深度配对保证外层分支边界正确
  （选中分支整体保留、未选中剔除），内层候选若不可确定 → 保守保留危险命令。
  危险命令绝不会在剪枝结果中丢失（安全关键，见 tests/test_script_engine.py
  ::TestNestedBranchesSafety）。

**嵌套分支处理**（`_find_block_end` / `findBlockEnd` 深度配对）：`.find("esac")` /
`indexOf('esac')` 在嵌套时会取到内层关键字导致外层切错；深度计数（`case`+1、
`esac`-1，归零才结束）保证每个 case 只配对自己的 esac。if/fi 同理。线性 O(行)，
无递归遍历开销。

> 关键区别：**case/if 的"不能证明可达"= 保留扫描；"能证明不可达"= 剔除**。
> 前者保证不漏报，后者才消除误报。宁可多拦，不可漏。

## 五、性能预算

重构目标是**运行期性能/内存与旧版持平**（用户硬约束）。实测（Python，Linux profile）：

| 场景 | 重构前 | 重构后 | 说明 |
|---|---|---|---|
| 1000 行单脚本 | 25.6ms | 26.9ms | 持平 |
| 3 层链 | 31ms | 29.1ms | 持平 |
| 6 层链 | 37ms（只追4层） | 57ms（追6层） | 层数↑单层成本↓ |
| 15 层链 | 35ms（只追4层） | 141ms（追15层） | 全追踪 |
| 峰值 RSS | 23.7MB | 23.8MB | 持平 |

深层链耗时上升**完全来自追踪层数变多**（每层 ~9ms 读取+解析），不是引擎变慢。
141ms 仍远低于 L3 LLM 的秒级成本。TS 端行为一致（各层逻辑镜像）。

## 七、如何扩展

**加一种新语言**（如 Node，Python 已落地）：
1. 新建 `backends/<lang>_backend.py` / `script-engine/backends/<lang>-backend.ts`，
   实现 `LanguageBackend.parse()`。
2. 产出统一 IR：`reachable_content` = 静态可达部分，`calls` = 可追踪的子调用（含参数）。
3. 在 `tracker.py::_pick_backend` / `tracker.ts::pickBackend` 注册扩展名 → backend 映射。
4. 双端镜像 + 补 JSON 用例（一拦一放）+ 双端同步断言。

**调预算**：改 `tracker.py` / `tracker.ts` 的 `DEFAULT_*` 常量，双端同步。
